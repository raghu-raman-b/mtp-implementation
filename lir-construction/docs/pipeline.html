Lecture planner: how the LIR is built

From subtitle files to a guided, checked, ready-to-view course, on one 12 GB GPU. Generated 2026-10-30 16:37 from the current outputs.

Overview

The pipeline compiles one course at a time. Subtitle files and lecture titles go in; one LIR (Lecture Intermediate Representation) file per lecture and one course file come out, plus the downloaded videos. A viewer renders the LIR as a guided course: a primer before each lecture, the lecture in short segments, a quiz and summary after each segment, and a concept map and open questions at the end. Nothing at viewing time calls an LLM; the only model used there is a small sentence-embedding model on the CPU, for scoring open answers.

Five principles

  • Narrow calls for a small model. Each LLM call does one job on a short input (a segment, not a lecture, where possible), and its output is constrained to a JSON schema.
  • The LLM proposes, code decides. The model extracts and writes text. Code merges, assigns timestamps, enforces counts, picks activity types by rule and places the correct answer. The model never writes a timestamp or a pointer.
  • Everything cites the transcript. Every generated item carries the sentence IDs it came from.
  • Intent is recorded, not implied. Every phase and item carries the learning principle it serves, its ICAP mode, its Bloom level, and the rule that chose it.
  • Stages, not autonomous agents. Each stage runs over all lectures as one batch before the next stage starts.

Architecture

Stage 4 is the only step that walks the course in lecture order; its LLM calls are still batched for the whole course, and the registry is built by code in order. Validation layers 1 and 2 run inside every stage; layer 3 (the judge) is stage 6. Videos download on a background thread for the whole run.

Configuration: choosing the models

Which model plays which role is set in lir-construction/lir_config.toml; edit it and rerun generate_lir.py (or pass --config other.toml). Nothing else changes: the stages, prompts and checks are the same whichever model runs them. Cached answers are keyed by model, so switching a model recomputes only what that model produces.

Who does what: the division of work

The word “agent” here means a stage worker, not an autonomous agent: a fixed role with a narrow contract, called by the stage runner in a fixed order. No worker decides what to do next. Five workers share the run:

WorkerRole
Codedeterministic rules in Python: parsing, merging, counts, IDs, timestamps, choice of activity types, answer positions, graph building, checks, assembly
Generator · Gemma 4 E4B (Q8)proposes text: boundaries, sub-goals, key points, terms, objectives, edges, quiz items, recaps, questions, recall items, repairs
Judge · Gemma 4 12B (QAT Q4)verifies text: answers yes/no with a reason for every generated item
Embedder · all-mpnet-base-v2 (CPU)vectors for concept matching, edge retrieval, key-point scoring
Video worker · yt-dlp threaddownloads the lecture videos in parallel with everything else

The contract between them is propose / decide / verify. The generator proposes text inside a JSON schema; code decides everything structural (what to ask, how many, where the correct answer goes, which IDs and times apply); the judge verifies the text, and code routes its verdicts. A model never writes a timestamp, an ID, a pointer or a count.

Scheduling

Every stage is a barrier: it sends all of its calls for all lectures, waits for all of them, and only then does the next stage start. Inside a stage the calls are independent, so the client keeps up to n requests in flight (32 for the generator, 8 for the judge), subject to a token budget of 85% of the server's KV pool. Retries for failed layer-2 checks go back into the same batch. Stage 4 is the one place where order matters: its LLM calls are batched for the whole course, but code then walks the lectures in order to build the registry, so nothing in state[k] depends on a later lecture. Stage 6 alternates the two models on the GPU: judge all items → repair the failures → judge the repairs → …, at most two repair rounds.

How a lecture is represented

A lecture is represented in four layers, each defined on the one below. Everything that is generated points back to the bottom layer, the sentences, so every item can be checked against the transcript and linked into the video.

Sentences. Σ = (σ0, …, σN−1), σi = (i, tstarti, tendi, texti), with tstart non-decreasing. Here N = 200.

Segmentation. A partition of Σ into contiguous intervals S = (s1, …, sM), sj = [aj, bj], a1 = 0, aj+1 = bj + 1, bM = N − 1, with 120 s ≤ dur(sj) (merged by code) and dur(sj) ≤ 720 s or flagged. Here M = 10.

Annotation. α(s) = (subgoal, c, Ks, Ts, Us): a verb-first sub-goal; a content type c ∈ C (10 types); key points Ks = {(k, text, Ik)}, 2 ≤ |Ks| ≤ 5, Ik ⊆ s; key terms Ts = {(term, definition, I)}, I ⊆ s; used concepts Us. Every term t is mapped to a concept κ(t) ∈ V of the course graph (next section).

Goal hierarchy. Objectives O = (o1, …, oR), 2 ≤ R ≤ 6 (or M when M < 2), a partition of S into contiguous runs; one lecture goal g. Course goals Gc are built bottom-up from the lecture goals, each over a set of lectures.

Phases. Φ = (φ0, φ1, …, φ2M+1) = (primer, seg(s1), act(s1), …, seg(sM), act(sM), constructive). A renderer walks Φ in order and draws each φ by its type; nothing else is needed to play the lecture.

Intent. Every phase and every item x carries ι(x) = (P, mode, bloom, rule, rationale, src): principles P ⊆ Π (11 named principles), ICAP mode ∈ {passive, active, constructive}, a Bloom level, the code rule that chose x, a templated rationale, and its sources src(x) ⊆ Σ.

Invariants (checked by code)

  • Grounding: src(x) ⊆ s(x) for items generated from a segment, and src(x) ⊆ Σ for lecture-level items.
  • Coverage: S partitions Σ; O partitions S into contiguous runs; every segment has exactly one objective.
  • Order: lecture k refers only to concepts with intro(v) ≤ k; recall items point only to lectures < k.
  • Counts: 4 quiz items per segment before judging (exactly one correct option each), 4 open questions per lecture, 3–5 key points per question with ≥ 2 keywords each.
  • Origin: every LLM-produced item has an origin record (model, prompt ID and version, input hash, validator result, retries, tokens, latency).

The graph representation

The course is represented as one typed, evidence-carrying graph that grows lecture by lecture. Everything that crosses a lecture boundary (recall items, links to earlier material in summaries, interleaved quiz items, the concept maps) is a query on a snapshot of this graph.

Graph. G = (V, E, λ). Concepts v ∈ V carry a name, aliases A(v), a definition d(v) (or none), an introduction point intro(v) = (lecture, segment, sentence, t), mentions M(v) (segment and sentence IDs), and a salience. Edges are typed triples e = (u, r, w) ∈ V × R × V with R = {prerequisite_of, part_of, example_of, contrasts_with, leads_to, used_in}; each carries a link phrase λ(e) for the concept map and evidence ev(e) = (lecture, I), I ⊆ Σlecture. Edges are deduplicated on (u, r, w); contrasts_with is symmetric.

Canonicalization. A term t from stage 2 is mapped to a concept by κ, applying the first rule that fires: (1) normalized name or alias equal (case, plural, hyphens; “Augmented Reality (AR)” gives the alias AR); (2) acronym rule: an acronym equals the initials of another name of ≥ 2 words; (3) cos(emb(t), emb(v)) ≥ 0.93 → same concept; (4) 0.78 ≤ cos < 0.93 → the generator answers a yes/no question; (5) otherwise a new concept, but only if t is defined somewhere; a term that is only used, never defined, joins an existing concept or is dropped. Rules 1–2 and the order of evaluation make κ deterministic given the LLM's yes/no answers.

Snapshots. For lecture position k, Gk = (Vk, Ek) with Vk = {v : lec(intro(v)) ≤ k} and Ek = {e : lec(ev(e)) ≤ k}, mentions and definitions filtered the same way. Snapshots are monotone: Gk−1 ⊆ Gk. Each is saved as output/<course>/state/state_Lxx.json.

No leakage. Everything generated for lecture k is a function of (α(lecture k), Gk); the primer is a function of (α(lecture k), Gk−1, and the edges from lecture k's new concepts). Code checks this when assembling.

Salience. salk(v) = [ln(1 + |segments mentioning v up to k|) + 𝟙[d(v) defined] + ½ ln(1 + degk(v))] / maxu(·). It ranks the primer's key terms (≤ 8), the summary's key concepts (≤ 8) and the concept-map seeds.

Queries. With new(k) = {v : lec(intro(v)) = k} and Nk(x) the neighbours of x in Gk:

  • recall(k) = top-4 by salk−1 of {u ∈ Vk−1 : ∃ (u, r, w) ∈ Ek, w ∈ new(k), r ∈ {prerequisite_of, used_in}};
  • earlier_links(s) = {u : (u, ·, w) or (w, ·, u) ∈ Ek, w ∈ κ(s), u introduced before s};
  • interleave(s) = argmaxu salk(u) over u ∈ Vk−1 adjacent to κ(s) with d(u) defined;
  • map_ref(k) = the subgraph of Gk induced by V(k) ∪ (Nk(V(k)) ∩ Vk−1), where V(k) are the concepts mentioned in lecture k; seeds = top-4 of new(k) by salience plus the top-2 earlier anchors.

How inference runs

Both models run in llama-server (llama.cpp) inside the llm-engine toolbox, started and stopped by the pipeline. Only one fits on the 12 GB card at a time, so the pipeline swaps them: the generator runs stages 1–5, the judge takes over for stage 6, the generator comes back for repairs, and so on.

Batching

Each stage sends every prompt for every lecture at once. The client keeps up to 32 requests in flight; the server's continuous batching decodes them together. Because the KV pool is shared, the client also caps the tokens in flight (prompt plus expected output) at 85% of the pool, so several long lectures segmented at once cannot overflow it. Prompts that share a prefix reuse the server's prompt cache: segment-level prompts are ordered role line → segment transcript → task, so the annotation, quiz, summary and question calls on one segment share their transcript prefix.

Output tokens per second with thinking on, 64–128 annotation-style calls on Deep Learning transcript segments. Throughput peaks at 32 slots, the default.

Why not vLLM

vLLM is installed and wired in (--engine vllm), but Gemma's E4B carries 3.5 B parameters of embedding tables (per-layer embeddings) that vLLM keeps in bf16, about 7 GB. With FP8 transformer layers the model alone needs about 11 GB of the 12 GB card, leaving no room for the KV cache. The Q8 GGUF stores those tables in 8 bits and fits with 2.5 GB to spare.

Caching and cost logging

Every answer is written to output/<course>/cache/<stage>.jsonl, keyed by a hash of the model, prompt, schema and settings; a rerun after a prompt change recomputes only that stage. Every call logs its input and output tokens and latency; the per-lecture cost in the report splits each stage's wall time over lectures by how long their calls held a slot.

The stages, with a real example

Examples below come from Foundation for Virtual and Augmented Reality Systems, lecture L27 · Visual Perception & Displays I, as built. Each stage's prompt is shown in full under “Prompt”.

0 · Transcripts

Each subtitle file is parsed into cues, cleaned of sound tags ([SQUEAKING]), speaker labels (SARA BEERY:) and the OCW licence notice, and merged into sentences: a cue that ends mid-sentence joins the next. Every sentence keeps its start and end time and gets an ID; every later item cites these IDs. Lectures with no subtitle file (VR lectures 4 and 5) take the official NPTEL transcript and align its words to YouTube's automatic captions, which time every word, so the sentences keep the clean punctuation and get accurate times.

1 · Segment

One call per lecture with the best prompt from the segmentation study (event-segmentation/compare/REPORT.md: WindowDiff 0.09 against the human annotator, versus 0.28 for TextTiling). The model sees the numbered transcript and returns the sentence numbers that start a segment. Code then sorts them, merges segments under 2 minutes into the shorter neighbour, and flags segments over 12 minutes. Lectures over 28k prompt tokens are segmented in overlapping windows of 300 sentences.

2 · Annotate

Two narrow calls per segment. The first writes the sub-goal (verb first), the content type (one of ten) and 2–5 key points, each one atomic statement with its sentence IDs. The second lists key terms with definitions and the sentences that define them, plus concepts the segment uses without defining. Code checks that every cited ID is inside the segment, that the sub-goal starts with an allowed verb, and that each term actually occurs in its cited sentences.

Prompt annotate.subgoal_points v1
Task: describe this segment.
- subgoal: what the learner achieves in this segment, as one short phrase that starts with a verb, for example "Explain why ...", "Derive ...", "Compare ...", "Apply ...". Be specific to this segment, at most 15 words.
- content_type: the one type that best describes what the instructor mainly does in this segment:
  motivation (why the topic matters), definition (introduces what something is), mechanism_explanation (how or why something works), derivation_or_proof, procedure_or_algorithm (steps to follow), worked_example (solves a specific instance), comparison, application_or_demo, recap (summarises earlier material), discussion (questions, opinions, course logistics).
- key_points: 2 to 5 key points. Each is one atomic, self-contained statement of something the segment teaches (a fact, claim, step or result), understandable without the transcript, with the IDs of the sentences that state it.
Use only what is said in this segment.
Prompt annotate.terms v2
Task: list the key terms this segment defines, and the other concepts it relies on.
- key_terms: up to 6 technical terms or named concepts that the instructor defines, explains or introduces in this segment: the terms a student would put in a glossary for this subject. For each give the term as it is said (a short noun phrase, singular), a one-sentence definition faithful to what the instructor says, and the IDs of the sentences where it is defined or explained. Do not list generic words (such as "example", "system", "technology", "basic understanding"), course logistics, or names of people, institutions or courses.
- used_concepts: up to 8 other technical concepts of the subject that the segment uses or mentions without explaining them (short noun phrases; no generic words, people, institutions or courses).
If the segment defines nothing, return an empty key_terms list.

3 · Goal hierarchy

A tiny call per lecture: only the title and the list of sub-goals go in. Out come 2–6 objectives, each a contiguous run of segments, phrased as “You'll be able to …”, and one lecture goal. Code checks every segment is in exactly one objective and the runs are contiguous. Course goals are built bottom-up from the lecture goals in one more call.

Each objective covers a contiguous run of segments (no gaps, no reordering), and every segment belongs to exactly one objective. 4 · Course knowledge state

The registry is what makes cross-lecture links possible. For each lecture in order, terms are canonicalized against it: same normalized name, an alias such as “(AR)”, or an acronym that spells another name's initials is the same concept; otherwise embedding similarity decides (≥ 0.93 same, 0.78–0.93 a yes/no LLM call, below that a new concept). Concepts only used, never defined, join an existing concept or are dropped. One call per lecture then extracts typed edges (prerequisite of, part of, example of, contrasts with, leads to, used in), each with a link phrase and evidence sentence IDs. Finally state[k] is saved: the registry and edges as of lecture k. Anything generated for lecture k reads only state[k]; the primer reads state[k−1].

Every edge reads as a sentence "src rel dst", and that sentence must be true. Relation types:
- prerequisite_of: src must be understood before dst (e.g. "derivative prerequisite_of gradient")
- part_of: src is a component of dst (e.g. "encoder part_of transformer")
- example_of: src is an instance of the more general dst (e.g. "virtual reality example_of extended reality"; the specific thing is src, the general category is dst)
- contrasts_with: src is set against dst
- leads_to: src causes or produces dst
- used_in: src is used as a tool or step in dst
src and dst must be two different concepts.
label: a link phrase of 2 to 5 words that sits between the two concept names on a concept map, read as "src label dst", e.g. "is a kind of", "is computed by", "is needed for". Do not repeat the concept names in the label.
evidence: the sentence IDs from the evidence list that support the edge.
At least one end of every edge must be a concept from this lecture. Give at most 20 edges, the most important first. Do not invent relations the lecture does not support.

How does the iris regulate the amount of light entering the eye?

· By adjusting the curvature of the cornea. — This is incorrect because the cornea is the transparent outer layer that light passes through, not the mechanism for light control.
· By changing the sensitivity of the retina. — This is incorrect because the retina is the light-sensitive tissue, and its sensitivity is a property, not a mechanism controlled by the iris.
· By filtering light before it reaches the lens. — This is incorrect because the iris controls the aperture (pupil), not the filtering properties of the light itself.
✓ By dilating or constricting the pupil size. — This is correct because the iris controls the pupil size, allowing more or less light to enter the eye.

What type of energy do photoreceptors detect to initiate visual perception?

· Thermal energy — Thermal energy is heat, and while the eye is sensitive to temperature, photoreceptors are specifically designed to detect light.
· Kinetic energy — Kinetic energy relates to motion and is not the primary stimulus detected by photoreceptors.
· Chemical energy — Chemical energy is stored energy and is not the form of energy that light uses to stimulate the retina.

How does the combination of engineered and natural lenses allow us to perceive immersive visual content in extended reality systems?

Self-explanation chosen because S1 explains how a mechanism works.

Reference answer. Light is emitted from the displays and arrives on our retinas, which is part of our eye. In VR headsets, a system of both engineered and natural lenses guides this light. The LIR files

Two kinds of JSON file. course.json holds the lecture list, course goals, the concept registry (name, aliases, definition, where introduced, every mention, salience), the edges with evidence, and the concept embeddings. Each Lxx.json holds the sentences with timestamps, the roadmap, the segments and an ordered list of phases: any UI, or a VR environment, renders a lecture by walking the list and drawing each phase by its type (primer, segment, active, constructive).

Intent on every phase and item: principle, icap_mode, bloom_level, rule_id, rationale, sources. Origin, one record per generated item: model, engine, prompt ID and version, input hash, validator result, retries, tokens, latency. Quality: the judge's results per check. The viewer and runtime scoring

python3 serve.py serves the viewer at http://localhost:8000. The home page shows the course goals and the full roadmap (lectures → objectives → segments, with progress) and a Start button; the whole course LIR is loaded at once. A lecture walks its phases: the primer, then each segment's video (local file, seeking supported; optional captions with the current sentence highlighted; click to jump, double-click to highlight), then its quiz and summary, and finally the concept map and open questions. Highlights resurface in the segment summary and at the end of the lecture. Progress and answers are kept in the browser.

Scoring open answers (CPU)

An answer is scored against the question's key points, not one ideal answer. A key point counts as covered if the answer contains at least m words of its keyword set (stemmed, with WordNet synonyms), or if some sentence of the answer has cosine similarity ≥ τ with the key point (the key-point embeddings are stored in the LIR; only the learner's sentences are embedded at runtime, on the CPU). The share covered gives the tier: Excellent ≥ 0.75, Good ≥ 0.5, Acceptable ≥ 0.25, else Try again. The feedback names the tier, gives a hint from one missed key point, lists the covered and missed key points, and lets the learner revise before revealing the reference answer.

m and τ are calibrated without a human: the generator writes a good, a partial and a wrong answer to a sample of questions, and code grid-searches m and τ so good answers land at ≥ 0.75, partial ones in [0.25, 0.75) and wrong ones below 0.25. Current setting: m = 2, τ = 0.8, 57% agreement on 42 answers; mean score: good 0.796, partial 0.54, wrong 0.292.

Scoring concept maps

Each learner concept is matched to a registry concept by name or alias first, then by embedding similarity. A learner link matches a reference edge if it joins the same two concepts; a similar label earns a bonus. The score is the share of the reference edges among the learner's matched concepts that were found. Links not in the reference are marked, not penalized; the reference map can be shown at any time.
