[37/S0/F0] The outcome of contextual inquiry, a usability requirement gathering method, can be utilized as design guidelines, design recommendations, or design principles, and also as functional requirements.
[37/S0/F1] Functional requirements are requirements specified in terms of functions that have a well-defined input and a well-defined output, and this functional specification makes them easy to convert to code so that the transition to code design becomes easier.
[37/S1/F0] In the note-taking application example, guidelines framed from observations are generic and specify what the application should or should not do, not how to do it.
[37/S1/F1] Some of the guidelines that can be framed from the observations in the note-taking application example state that the application should support viewing of upcoming deadlines for assignment submission for the current day and the next seven days, viewing of scheduled meetings for the current date, viewing of the timetable on any given day, and viewing of lecture schedules on any given day.
[37/S1/F2] In the note-taking application example, guidelines based on behaviors observed in the context of use are used to include those behaviors in the overall system, thereby ensuring that the user is involved in the design based on observations and feedback.
[37/S2/F0] A functional requirement (FR) is a formally specifiable requirement that is easy to convert into code because it specifies a system feature as a black-box function with a well-defined input, a well-defined output, and an optional description of its purpose.
[37/S2/F1] Usability requirements, which are non-functional requirements (NFRs), can be converted into functional requirements (FRs) and added to the already obtained set of functional requirements, so that usability requirements are directly incorporated into the system through code and support code design.
[37/S2/F2] A software requirements specification (SRS) is the textual document that specifies all requirements of a system, both functional and non-functional, and it includes the formal specification of the functional requirements.
[37/S2/F3] In a software requirements specification (SRS), requirements are generally organized in a hierarchy with identifiers such as R1 for a top-level requirement and R1.1 for a sub-requirement, and each requirement identifier represents a function with a clearly defined input, a clearly defined output, and an optional description of what it does.
[37/S2/F4] The output of contextual inquiry is a group-wise organization of the notes taken during observation, and it can be used as design guidelines to ensure usability that cannot be immediately converted to code or, for some of them if not all, converted into functional requirements (FRs) that can be directly implemented as code.
[37/S2/F5] In the calendar app for college students example, the functional requirement R1 views takes a date as input and generates a specific view such as timetable, submission deadlines, or meeting list, with subrequirements R1.1 timetable view (date input, day timetable output), R1.2 deadline view (date input, submission deadlines output), and R1.3 meeting schedule (date input, list of meetings scheduled on the day output).
[37/S3/F0] Usability requirements for the Majuli virtual reality (VR) Tour were gathered by making field trips to Majuli, interviewing people, observing people in their natural work settings, and collecting data in the form of notes.
[37/S3/F1] The Majuli virtual reality (VR) Tour is intended for people who do not reside on Majuli rather than residents, because residents are least likely to use it since they are already on the island.
[37/S3/F2] Three potential user groups in the Majuli virtual reality (VR) Tour case study were identified through field trips, interviews, observations, and local people's experience of typical visitors and their activities: students or learners interested in knowing about the island, tourists interested in exploring tourist spots or other interesting places on the island, and pilgrims interested in religious places and practices.
[37/S3/F3] The usability of the Majuli virtual reality (VR) Tour is claimed only for the three identified user groups—students or learners, tourists, and pilgrims—and it is not claimed to be usable for any person in any work context or task.
[37/S3/F4] Contextual inquiry (CI) in the Majuli virtual reality (VR) Tour case study was conducted after the user groups were identified, on samples from those user groups, to learn their needs and expectations, identify the system features to be supported for each group, and identify specific issues for those groups related to broad design challenges.
[37/S3/F5] A key design challenge in the Majuli virtual reality (VR) Tour case study was to provide a comprehensive view of a large geographical area with large multimodal data while avoiding cyber sickness, because exploring the entire island with all collected data is time consuming and may cause cyber sickness.
[37/S3/F6] The large geographical area and cyber sickness challenge in the Majuli virtual reality (VR) Tour case study was addressed by allowing each user group to access only a subset of the collected data, with each subset identified through contextual inquiry (CI) based on what that group typically does.
[37/S3/F7] The data-subset restriction in the Majuli virtual reality (VR) Tour case study reduced the expanse of information and the need to explore everything in detail, reduced the possibility of cyber sickness, and increased interest for each group, whereas making the entire data set accessible to all users could confuse users, reduce their interest, and lead to cyber sickness.
[37/S3/F8] Accurate location information in any virtual reality (VR) tour is crucial, especially for large geographies, because it prevents disorientation and gives users more confidence and purpose by telling them where they are in the geographical space.
[37/S3/F9] Location awareness in the Majuli virtual reality (VR) Tour case study was identified during contextual inquiry (CI) as an issue for users exploring a large space, and a possible resolution was to add a location awareness feature, later to be converted into functional requirements during system design.
[37/S3/F10] A key design challenge in the Majuli virtual reality (VR) Tour case study was to provide both tangible and intangible heritage experiences and to combine them for a seamless user experience.
[37/S3/F11] Another key design challenge in the Majuli virtual reality (VR) Tour case study was interaction aid for enhanced user experience, which includes navigation support to cover a large geography, user-friendly interfaces, and increased presence through natural interactions.
