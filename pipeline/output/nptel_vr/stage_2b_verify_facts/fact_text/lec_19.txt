[19/S0/F0] The role of virtual reality (VR) software is to drive virtual reality hardware or augmented reality (AR) hardware, not merely to drive the hardware, so that the hardware generates appropriate stimuli that are appropriately received to stimulate human sense organs, creating a virtual reality experience that utilizes human senses.
[19/S1/F0] In a virtual reality (VR) system, bidirectional data flows occur between the virtual reality hardware, the surrounding physical world, and the user (organism), with tracking and stimulation occurring between the user and the virtual reality hardware.
[19/S1/F1] The data flow between a user and virtual reality (VR) hardware works by the user operating input devices to generate data that is sent to and processed by the virtual reality system, and by sending the processed data back to output devices that generate stimuli to suitably affect the user's sense organs.
[19/S1/F2] The data flow between a user and virtual reality (VR) hardware requires proper interaction design and modeling for the user's interaction with input devices, perceptual design and modeling so that stimuli generated by output devices suitably stimulate the user's sense organs, and software to process input data and generate output data.
[19/S1/F3] The software part of the virtual reality (VR) data-flow diagram is represented by two components: the virtual reality engine and a software-and-database component.
[19/S2/F0] Creating a virtual reality (VR) experience involves three activities: creating the virtual environment, which can also be called environment modeling or object modeling; creating the stereoscopic output view, which can also be called rendering; and incorporating interactions, which involve tracking hardware.
[19/S2/F1] In the context of creating a virtual reality (VR) experience, the terms view or rendering are used in a broad sense to refer not only to visual output but also to output for other senses.
[19/S2/F2] From the developer's point of view, virtual reality (VR) software should allow the developer to create a VR application by providing assistance in the three activities of creating the virtual environment, rendering the stereoscopic output view, and incorporating interactions.
[19/S2/F3] Ideally, virtual reality (VR) software should let a developer provide only high-level descriptions from which all low-level details are automatically determined; the developer can then use middleware between the developer and the hardware, following well-known patterns and calling well-designed software libraries to avoid micro-level activities; and the software should also allow the developer to design functions from scratch for original work rather than depending on middleware.
[19/S2/F4] In practice, a virtual reality (VR) developer may need to implement much functionality from scratch instead of providing only high-level descriptions that software automatically converts to low-level details.
[19/S2/F5] In practical virtual reality (VR) development, a developer may use a software development kit (SDK) for a particular headset or platform to handle lowest-level, platform-specific operations such as device drivers, head tracking, and display output; SDKs are platform dependent, with a platform being a combination of hardware and operating system (OS), and the developer may not handle the lowest-level operations directly but must understand the SDK that handles them.
[19/S2/F6] A game engine can be used as middleware for virtual reality (VR) application development; game engines are generally developed for games, which need not be immersive VR games, and can be adopted for VR development or specific VR engines can be developed.
[19/S2/F7] Using a game engine as middleware can avoid substantial initial effort but may be cumbersome for implementing ideas not part of standard video games, and if the engine is not specifically a virtual reality (VR) engine, the developer loses some flexibility.
[19/S3/F0] The virtual world generator (VWG) is an abstraction of the whole virtual reality (VR) software system, treated as a black box whose internal operation is not considered.
[19/S3/F1] The virtual world generator (VWG) receives input from low-level systems such as a head tracker that estimates the user's head position and orientation, a keyboard, a mouse, and a game controller, and other input devices, and simultaneous input events are arranged in a queue so that they can be processed systematically.
[19/S3/F2] The virtual world generator (VWG) must maintain an internal reality that appears real to the user, convert incoming input into output so that renderers can extract information and calculate outputs for their displays, and keep output devices synchronized with the input data to maintain an input-output match.
[19/S3/F3] The virtual world generator (VWG) can use several output renderers, including a visual renderer that generates a visual display, an aural renderer that generates an aural display sensed by the ears, and a haptic renderer that generates a haptic display sensed by the skin, along with other possible renderers.
[19/S3/F4] A completely synthetic virtual world requires defining a triangular mesh in a three-dimensional space and maintaining material and physical surface properties that indicate how the surfaces interact with light, sound, and forces.
[19/S3/F5] Computer graphics addresses computer-generated images from synthetic models, and the software that helps a developer build a virtual reality (VR) experience should support computer-graphics operations.
[19/S3/F6] A virtual world can also be a recorded physical world, made realistic by capturing the real world with cameras and using computer-vision and simultaneous localization and mapping (SLAM) techniques, so virtual reality (VR) software may require support for SLAM or computer-vision techniques.
[19/S3/F7] One possibility for creating a virtual world is texture mapping, in which camera images of a real object are mapped onto a synthetic object; this is a common computer-graphics operation that virtual reality (VR) software should ideally support.
[19/S4/F0] Matched motion in virtual reality (VR) is the maintenance of correspondence between a user's motions in the real world and the virtual world.
[19/S4/F1] A matched zone is a place where the real world and the virtual world perfectly align; it corresponds to the safe real-world region where a user's physical movement is restricted, although the virtual world is not similarly confined, and movement within that region is translated to movement in other parts of the virtual world.
[19/S4/F2] In an immersive virtual reality (VR) application that is not carefully implemented, an obstacle mismatch can occur when a virtual obstacle blocks the user without a corresponding physical obstacle in the matched zone, or when a physical obstacle exists in the matched zone without a corresponding virtual obstacle.
[19/S4/F3] In virtual reality (VR), the real-world motions reflected in the virtual world vary among virtual reality experiences: head motions must be matched so the visual renderer uses the correct viewpoint, and other body parts require tracking and matched motion when the user needs hand-eye coordination or looks at those body parts during the experience.
[19/S4/F4] Virtual reality (VR) software should include developer support for resolving matched-motion challenges, such as deciding which real-world motions to reflect and creating a correspondence between a user's physical motion in the matched zone and a different virtual motion.
[19/S4/F5] User locomotion in virtual reality (VR), which is closely related to matched motion, is moving oneself in the virtual world while one's physical motion in the real world is not matched; it is motivated because users often want to move well outside the matched zone.
[19/S4/F6] Teleportation in virtual reality (VR) is a locomotion operation in which a user can pull up a menu, point to a desired virtual location, and be sent to that location without making any physical movement.
[19/S4/F7] A popular option for user locomotion in virtual reality (VR) is operating a game controller, mouse, or keyboard so the user's avatar can walk, run, jump, swim, climb, board a vehicle, and operate its controls while the user remains seated; the vehicle option is a vehicle metaphor.
[19/S4/F8] Virtual reality (VR) locomotion operations that let the user avoid physical movement may lead to cyber sickness, which increases with exposure duration and other factors.
[19/S4/F9] Support for user locomotion, including different sorts of locomotion so that cyber sickness can be addressed, should be part of virtual reality (VR) software.
