[20/S0/F0] Physics support is a required key support in a virtual world generator, in addition to computer graphics and computer vision support for rendering, locomotion support, and matched motion support.
[20/S0/F1] A virtual world generator usually implements some physics, depending on the kind of generator and the extent of support it can provide.
[20/S0/F2] The basic purpose of physics support in a virtual world generator is to make the virtual world appear to behave like the real world, so that events observed in the real world have similar events in the virtual world.
[20/S0/F3] In most cases, object motion in a virtual world generator should be governed by basic laws of mechanics; support for basic laws should be good enough, while support for advanced laws can make motion more realistic, which sometimes may be desirable.
[20/S0/F4] Physics support in a virtual world generator should make a dropped ball accelerate toward the ground due to gravity rather than move it at constant speed.
[20/S0/F5] Collision support in a virtual world generator should ideally include collision detection, which determines whether two or more bodies intersect, and collision response, which determines how they should behave after a collision occurs.
[20/S0/F6] Physics support in a virtual world generator should also replicate other physical-world phenomena, such as how light propagates, how light interacts with different surfaces, the effects generated, the sources of light and resulting illumination effects, and how sound and smell propagate.
[20/S1/F0] A networked collaborative virtual reality (VR) experience is a collaborative virtual reality experience created over a network, in which a shared virtual world is maintained by a system or a server, although such a network experience may not be required everywhere.
[20/S1/F1] In a networked collaborative virtual reality (VR) setting, each user has a distinct matched zone; matched zones may overlap in the real world, but most often they are disjoint and distributed around the Earth, so unwanted physical collision must be avoided when users are close, while users spread around the globe have no possibility of physical collision.
[20/S1/F2] Within the shared virtual world of a networked collaborative virtual reality (VR) experience, user interactions, including collisions, must be managed by the virtual reality system whether users are close or spread around the world.
[20/S1/F3] In a networked collaborative virtual reality (VR) setting, the virtual world generator (VWG) should support eye movements, facial expressions, and body language when social interaction is important, and the burden of matched motion may increase as users meet each other.
[20/S2/F0] To build a virtual reality (VR) experience, a developer can either build a virtual world generator (VWG) from scratch using a basic software development kit (SDK) for a specific headset, device, or platform, or use a ready-made virtual world generator (VWG) customized by choosing menu options and writing high-level scripts.
[20/S2/F1] A basic software development kit (SDK) for a headset, device, or platform is typically expected to provide basic drivers to drive the hardware, interfaces or application programming interfaces (APIs) to access tracking data, and application programming interfaces (APIs) to make calls to graphical rendering libraries; in a virtual world generator (VWG), basic drivers and tracking cover some aspects and rendering covers other aspects, but not every aspect of locomotion or matched motion, physics, or networked collaborative virtual reality (VR) experience is typically taken care of by the software development kit (SDK).
[20/S2/F2] When building a virtual world generator (VWG) from a basic software development kit (SDK), the developer must build, at the very least, the physics support of the virtual world from scratch, handling problems such as movement of an avatar, collision detection, occurrence of collision and the response to it, lighting models, and audio support; sometimes collaborative virtual reality (VR) experience support is also required.
[20/S2/F3] Using a basic software development kit (SDK) to build a virtual world generator (VWG) from scratch gives the developer maximum control and the ability to optimize performance because the developer can choose and implement the algorithms for physics support according to performance, rather than being forced to use whatever comes with a package.
[20/S2/F4] Using a basic software development kit (SDK) to build a virtual world generator (VWG) from scratch imposes a difficult implementation burden and requires a lot of effort to understand and implement the overall system from scratch.
[20/S2/F5] OpenSimulator and Unity3D can provide ready-made virtual world generator (VWG) support; OpenSimulator is an open-source alternative to Second Life designed to support developers in building a virtual society of avatars, and Unity3D is a popular game engine adapted to work for virtual reality (VR).
[20/S2/F6] A ready-made virtual world generator (VWG) or higher-level engine makes it easy for developers to create a virtual reality (VR) experience in little time because it comes with supports, including support for collisions or physics, so the developer does not have to build things from scratch.
[20/S2/F7] A ready-made virtual world generator (VWG) or engine is harder to use for highly original experiences not imagined by the engine builder because it comes with its own function supports and algorithm implementations that the developer must use, which restricts the developer, although it reduces effort.
[20/S3/F0] A virtual reality (VR) engine, also called a game engine, is middleware that sits between hardware and higher-level application software, abstracts hardware functionalities for developers of extended reality (XR) applications, and provides support for hardware abstractions.
[20/S3/F1] A game engine is a software development environment for building extended reality (XR) experiences, and a developer can build their own application on top of it.
[20/S3/F2] A game engine can be thought of schematically as comprising multiple components, for example a physics engine, a rendering engine, an audio engine, and a user interface.
[20/S3/F3] An authoring tool for a game engine lets a developer access the different functionalities supported by the game engine in order to develop their own software that runs on top of the game engine.
[20/S3/F4] An authoring tool for a game engine may provide loading options, feature-setting options, and logic-setting options, and its logic setting can sometimes be done through scripting, which can be part of a game engine development environment.
[20/S3/F5] A development environment that comprises a game engine plus other components can include the entire authoring tool, and Unity three-dimensional (3D) Development Environment or Unity Hub is an example of such a development environment.
[20/S3/F6] Typically, game engines have core functionalities that include rendering support, physics support, audio support, scripting for customizing various features, networking support primarily for multiplayer collaborative virtual reality (VR) experiences, and low-level support for platform-specific tasks, including memory management and other activities, with threading and localization support being part of memory management.
[20/S4/F0] A rendering engine in a game engine helps generate animated three-dimensional (3D) graphics by rendering methods such as rasterization or ray tracing, a particular rendering engine may support a particular rendering method, and the rendering method adopted may depend on the sophistication level of the engine or platform.
[20/S4/F1] Rasterization is less computationally intensive than ray tracing.
[20/S4/F2] A rendering engine is typically built on one or multiple rendering application programming interfaces (APIs), such as Direct3D, Open Graphics Library (OpenGL), or Vulkan, which provide software abstractions of the graphics processing unit (GPU).
[20/S4/F3] A graphics processing unit (GPU) is the hardware component that is used for speeding up the rendering process.
[20/S4/F4] In a typical virtual reality (VR) system that uses a game engine as middleware, the layers from lowest to highest are hardware, rendering application programming interfaces (APIs), game engine, and application software, and the hardware layer includes a graphics processing unit (GPU), a central processing unit (CPU), and memory.
[20/S4/F5] An audio engine is a part of basic game engine support that consists of algorithms related to loading, modifying, and generating sound through a speaker system.
[20/S4/F6] An audio engine can perform its calculations on a central processing unit (CPU) or on a dedicated application-specific integrated circuit (ASIC), so it does not require a graphics processing unit (GPU), and audio engines are not typically associated with a GPU because a GPU is generally associated with graphics or rendering.
[20/S4/F7] An audio engine can be built on top of abstraction application programming interfaces (APIs) such as Open Audio Library (OpenAL), Simple DirectMedia Layer (SDL) audio, X audio 2, and Wave audio.
[20/S4/F8] A physics engine is one of the crucial components of a game engine and is responsible for emulating the laws of physics realistically within the application by providing a set of functions for simulating physical forces and collisions acting on various objects within the scene at runtime.
[20/S4/F9] The rendering, audio, and physics engines are often basic components of a game engine, but not all game engines contain all of these components.
[20/S4/F10] Unity 3D, Unreal Engine 4, CryEngine, Godot, Lumberyard, and Amazon Sumerian are examples of game engines.
[20/S4/F11] Based on the latest market-share statistics, Unity 3D and Unreal Engine are the most popular game engines, with Unity 3D occupying almost 51% of the game-engine market share, Unreal Engine occupying 28%, and all other game engines together occupying the rest.
[20/S4/F12] Unreal Engine's major features are freely available, whereas Unity 3D is proprietary, has a free version with limitations, and offers more flexibility in its proprietary versions.
[20/S5/F0] Deployment of a virtual reality (VR) application can be native application deployment, which requires software development kits (SDKs) tailored to the platform and hardware, or web application deployment, which allows the experience to be obtained remotely without a specific device.
[20/S5/F1] In deployment, a platform typically means the operating system (OS) plus the hardware, with Windows or Mac OS for desktop platforms and Android or iOS for mobile platforms.
[20/S5/F2] A software development kit (SDK) is a collection of software development tools in one installable package specific to a hardware and operating system (OS) combination, providing fundamental tools to design, build, and test virtual reality (VR) experiences for specific platforms.
[20/S5/F3] Native deployment software development kits (SDKs) can be categorized in two ways: by application type, as virtual reality (VR) or augmented reality (AR) applications, and by availability, as proprietary or open source.
[20/S5/F4] Head-mounted displays (HMDs) are the most popular device types for virtual reality (VR) experiences.
[20/S5/F5] Different head-mounted displays (HMDs) use different virtual reality (VR) software development kits (SDKs): the HTC Vive system can use the OpenVR SDK by Valve, the SteamVR SDK, or the VRTK SDK; the Oculus Rift uses the Oculus SDK; the Samsung Gear VR uses the Oculus Mobile SDK; the Sony PlayStation uses the PSVR SDK; and Google Daydream View or Google Cardboard uses the Google VR SDK.
[20/S5/F6] The Google virtual reality (VR) software development kit (SDK) is open source but is no longer very much supported.
[20/S6/F0] Web deployment tools can be broadly categorized as cloud hosting and rendering over a network tools, libraries for development support for deployment over the web, complete development and deployment tools for applications on the web, generic development editors for writing code for web-based deployment, and software development kit (SDK) support, including native software development kits and software development kits primarily meant for web deployment.
[20/S6/F1] Cloud hosting and rendering support tools for web deployment only provide hosting and rendering over a network.
[20/S6/F2] Examples of cloud hosting and rendering support tools include Azure Remote Rendering for three-dimensional (3D) rendering, NVIDIA CloudXR, Immersive Stream for extended reality (XR), which works on Google Cloud, Eco3D, and Arbor XR.
[20/S6/F3] Some popular libraries for development support for deployment over the web include WebXR, Three.js, augmented reality (AR).js, three.xr.js, WaveXR, AFrame, Babylon.js, and ReactXR.js, and there are many more such libraries.
[20/S6/F4] WebXR uses WebGL.
[20/S6/F5] Three.js makes WebGL easier and is used for rendering.
[20/S6/F6] WaveXR is built on three.js.
[20/S6/F7] Complete development and deployment tools for applications on the web include ZappAir, 8thWall, MyWebAR, VRDirect, GmetriXR, InstaVR, PlugXR, Amazon Sumerian, and other such tools.
