Why this pipeline

Three versions were built on the same course in three weeks. Each one failed in ways that could be read in its output, and each failure changed the design. This part tells that story with the real failed outputs and the prompts that produced them, then compares the design with simpler ways of doing the same job, and says plainly which claims are measured and which are argued.

How we got here: v1, v2, v3

v1: one LIR file per lecture, built on a 12 GB card

v1 turned each lecture into a guided sequence: recall questions, short clips, a quiz and a summary after each clip, a concept map and open questions at the end. It ran on one RTX 5070 with Gemma 4 E4B and a cheap API judge. It worked end to end, and its documentation (the page this one follows) is honest about its gaps. Three of them shaped v3.

The three failures, with v1's shipped output and its prompt registry merges · no fact store · topic-change segments

1. Concepts were merged by their names. v1's registry rule: “the same name or abbreviation means the same concept; otherwise embedding similarity decides (≥ 0.93 the same, 0.78–0.93 the model is asked yes or no)”. An abbreviation is not a name: “ER” is also error rates, empirical research and entity-relationship. One wrong merge then pulls in the next. This is v1's most central concept, as shipped:

v1 · course.json, C001
{{S:v1_xr}}
v3 · knowledge/concepts.json, C0001
{{S:v3_xr}}

v3 fixes this at three places. A concept's name is always the full term, and an acronym is only ever an alias (decision D8, prompts/concept_extraction.txt rule 4). Stage 3a never merges two entries because they share an acronym; a shared acronym only makes them candidates. And stage 3b asks the model to decide from the facts, not from the names alone (prompts/concept_same.txt), with the rule that a wrong merge costs more than a missed one.

2. There was no store of what a lecture says. v1 wrote key points and key terms per part and judged each one. A term the judge rejected left the registry with its links, which is why the course ended with 883 concepts. A question that no key point happened to cover had nothing to be answered from. v3 makes the fact the unit: one complete point of subject knowledge, with the sentences that state it. Concepts, relationships, definitions, activities and answers are all built from facts, so they all cite sentences.

3. Segments were cut at topic changes. v1 used the best prompt from a segmentation study (WindowDiff 0.09 against a human annotator on lecture 1, see the measured comparison). On the whole course it gave parts “4.7 minutes long on average; 16 are flagged as long”. The same prompt on the large v2 run gave “36 parts over 10 min and one of 28 min (L51/P04: a whole worked problem that the ‘stand alone’ rule would not cut)” (notebook, record of 2026-11-09). The prompt:

v1 prompt segment.standalone v3 lir-construction/pipeline/prompts.py on branch v1 
{{S:v1_segment_prompt.txt}}

“Each segment must stand alone” sounds harmless. A capable model reads it literally: its thinking on lecture 51 in v3's run 3 says “'So, given this background…' … Therefore, Segment 2 and 3 must be merged.” (analysis/segmentation/report.md). v3 defines a segment by its sub-goal (what the learner can do after it), limits “stand alone” to real dependencies and says outright that connectives are not one, and moves the length rule into code that only says “looks too small / too big” (stage 1). Result: 386 segments, none over 15 minutes.

v2: addresses, judges everywhere, and a prompt that grew with the course

v2 (LIR 2.1) gave every item a sentence address, a judge for every item with one rewrite, and a decision log. It moved to vLLM on an RTX PRO 6000. The small setup (E4B writes, 12B judges) built all 63 lectures; its analysis reads: “The knowledge per part is as good as v1 or better, and the v1 registry problems are mostly gone. Two steps failed silently on the second half of the course: 27 of 63 lectures have no links, and 20 lectures have no open questions. The run took 2.7× the planned time, because the 12B judge did most of the work.”

The four failures, with v2's links prompt and what it produced links overflow · judge cost · fragmented registry · open questions

The links prompt. One call per lecture listed every relation between that lecture's concepts. Its input block carried, for each concept, what every earlier lecture taught about it. The prompt text is fine; the input grows with the course:

v2 prompt links.lecture v1 lir-construction/pipeline2/prompts.py 
{{S:v2_links_prompt.txt}}
What it produced

“Every links.lecture call for those lectures was cut at length (56 of 92 calls; 30 retries). The prompt grows with every earlier facet of every concept: up to 63.9k input tokens against a 65.5k context. Result: 57% of concepts have no link.” Lectures L21, L27, L31 and L37–L63 (except L43, L46, L48) got none.

v3 finds relationships inside one segment, from that segment's facts only (stage 2c), and joins them across lectures in code (stage 3c). A prompt then never grows with the course: the 779 calls of 2c averaged about 3,700 input tokens (2,890,550 in all, stage_2c_concepts/llm/calls.jsonl). Every lecture has relationships; the course has 7,427. The price is decision D4 in the plan: a relationship between concepts taught in different segments is never found. It is listed under future work.

Judges set the run time. “2,711 judge + 1,035 rewrite calls: 58% of requests, 12.1 M of 18.0 M output tokens, 90%+ of it thinking, p50 latency 400 s.” v3 judges only what a learner sees (activities), caps thinking at 6,144 tokens, and measured its fact judge before letting it change anything. That measurement switched it off (stage 2b).

Fragmented, noisy registry. 1,019 of v2's 1,395 concepts appeared once; some aliases were sentences (“A virtual reality system is an artificial environment which…”). v3 checks every alias against the facts (alias_not_written: an alias must be written in a fact), never takes a sentence as a name, and joins the names with an exact merge plus a model decision per cluster.

Open questions dropped by a check. “70 questions dropped by the code check ‘each key point needs 2 keywords word for word in the reference answer’.” v3 ties a reference answer to its key facts (at least two) instead of keywords; every lecture has an open-question activity.

Against simpler approaches

Three simpler designs could answer a learner's question about a course. Here is how this pipeline differs from each, illustrated with real outputs. None of the three was run on this course yet, so this section is an argument from design; the experiment that measures it is described under Measured comparison, and a separate run is under way.

(a) Plain LLM

Ask a model, no course data

It answers from what it learned in training. It cannot say which lecture taught a thing or at what minute, it cannot say “this course does not cover that”, and its definitions are the textbook's, not the lecturer's.

(b) RAG over transcripts

Search the lecture text, answer from chunks

It can cite lectures. But a chunk of speech is full of “this”, “it”, “as we saw”, acronyms and asides; a chunk that mentions a term is retrieved as readily as the one that defines it; and no chunk holds “what do I need before lecture 9”.

(c) GraphRAG alone

An entity graph built from chunks

It adds entities and relations, often with community summaries. Without facts that cite sentences, a course order, a lecture graph and goals, it can relate concepts but not tell a learner where one is taught or what comes first.

What the knowledge layer gives that these do not, each with a real example:

  • Every claim leads to the video. An answer cites facts; each fact cites sentences; sentences have times. The learner sees “(lecture 8, 26:40)” and clicks it. From the vLLM benchmark (analysis/qa/bench_vllm_shipped.jsonl, B09): 
    {{S:qa_b09}}
  • “Not covered” instead of a made-up answer. Vergence-accommodation conflict is a real VR topic this course does not teach. The answer says so, then offers what the course does say (B02): 
    {{S:qa_b02}}
    A plain LLM would explain the conflict from its own knowledge, correctly perhaps, but not from this course.
  • Prerequisites from the lecture graph. “What do I need before lecture 30?” is answered from stage 4c, not from text that happens to match (B14): 
    {{S:qa_b14}}
  • Definitions with “where it is defined”. Each defined concept has one definition, written from its defining facts, with the lecture, segment and time where it is taught (the concept card).
  • Facts are cleaned before they are searched. A transcript sentence: “And it depends on the size and shape of the head, ears, and ear canal.” The fact built from it and two others: “Head-related transfer functions (HRTF) depend on the size and shape of the head, ears, and ear canal, and every person has a unique HRTF.” The pronoun is resolved, the acronym spelled out, the point whole. fact_lookup is retrieval too, but over 2,006 such facts, not over 206,605 words of speech.
  • Activities from the same verified store. A quiz question cites the facts that answer it, and a judge checked it against them (stage 5). Neither RAG nor a plain LLM produces a course's quizzes, crosswords and concept maps with that link.

Where it runs: the model on a server, the app with the learner

This split works because the pipeline does the heavy work in advance. What the server must do per question is small and stateless: run one model over a prompt of a few thousand tokens, a median of two times. Everything that is large (videos: 5.5 GB for the course) or private to the learner (progress, highlights, answers) stays local. The client already supports a model on another machine: a config with "launch": false and a port (or url) attaches to a running server, which is how every build stage reached the EC2 through an SSH port forward (pipeline/ec2.md).
