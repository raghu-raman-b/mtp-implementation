Why this pipeline

Three versions were built on the same course in three weeks. Each one failed in ways that could be read in its output, and each failure changed the design. This part tells that story with the real failed outputs and the prompts that produced them, then compares the design with simpler ways of doing the same job, and says plainly which claims are measured and which are argued.

How we got here: v1, v2, v3

v1: one LIR file per lecture, built on a 12 GB card

v1 turned each lecture into a guided sequence: recall questions, short clips, a quiz and a summary after each clip, a concept map and open questions at the end. It ran on one RTX 5070 with Gemma 4 E4B and a cheap API judge. It worked end to end, and its documentation (the page this one follows) is honest about its gaps. Three of them shaped v3.

The three failures, with v1's shipped output and its prompt registry merges · no fact store · topic-change segments

1. Concepts were merged by their names. v1's registry rule: “the same name or abbreviation means the same concept; otherwise embedding similarity decides (≥ 0.93 the same, 0.78–0.93 the model is asked yes or no)”. An abbreviation is not a name: “ER” is also error rates, empirical research and entity-relationship. One wrong merge then pulls in the next. This is v1's most central concept, as shipped:

v1 · course.json, C001
{{S:v1_xr}}
v3 · knowledge/concepts.json, C0001
{{S:v3_xr}}

v3 fixes this at three places. A concept's name is always the full term, and an acronym is only ever an alias (decision D8, prompts/concept_extraction.txt rule 4). Stage 3a never merges two entries because they share an acronym; a shared acronym only makes them candidates. And stage 3b asks the model to decide from the facts, not from the names alone (prompts/concept_same.txt), with the rule that a wrong merge costs more than a missed one.

2. There was no store of what a lecture says. v1 wrote key points and key terms per part and judged each one. A term the judge rejected left the registry with its links, which is why the course ended with 883 concepts. A question that no key point happened to cover had nothing to be answered from. v3 makes the fact the unit: one complete point of subject knowledge, with the sentences that state it. Concepts, relationships, definitions, activities and answers are all built from facts, so they all cite sentences.

3. Segments were cut at topic changes. v1 used the best prompt from a segmentation study (WindowDiff 0.09 against a human annotator on lecture 1, see the measured comparison). On the whole course it gave parts “4.7 minutes long on average; 16 are flagged as long”. The same prompt on the large v2 run gave “36 parts over 10 min and one of 28 min (L51/P04: a whole worked problem that the ‘stand alone’ rule would not cut)” (notebook, record of 2026-11-09). The prompt:

v1 prompt segment.standalone v3 lir-construction/pipeline/prompts.py on branch v1 
{{S:v1_segment_prompt.txt}}

“Each segment must stand alone” sounds harmless. A capable model reads it literally: its thinking on lecture 51 in v3's run 3 says “'So, given this background…' … Therefore, Segment 2 and 3 must be merged.” (analysis/segmentation/report.md). v3 defines a segment by its sub-goal (what the learner can do after it), limits “stand alone” to real dependencies and says outright that connectives are not one, and moves the length rule into code that only says “looks too small / too big” (stage 1). Result: 386 segments, none over 15 minutes.

v2: addresses, judges everywhere, and a prompt that grew with the course

v2 (LIR 2.1) gave every item a sentence address, a judge for every item with one rewrite, and a decision log. It moved to vLLM on an RTX PRO 6000. The small setup (E4B writes, 12B judges) built all 63 lectures; its analysis reads: “The knowledge per part is as good as v1 or better, and the v1 registry problems are mostly gone. Two steps failed silently on the second half of the course: 27 of 63 lectures have no links, and 20 lectures have no open questions. The run took 2.7× the planned time, because the 12B judge did most of the work.”

The four failures, with v2's links prompt and what it produced links overflow · judge cost · fragmented registry · open questions

The links prompt. One call per lecture listed every relation between that lecture's concepts. Its input block carried, for each concept, what every earlier lecture taught about it. The prompt text is fine; the input grows with the course:

v2 prompt links.lecture v1 lir-construction/pipeline2/prompts.py 
{{S:v2_links_prompt.txt}}
What it produced

“Every links.lecture call for those lectures was cut at length (56 of 92 calls; 30 retries). The prompt grows with every earlier facet of every concept: up to 63.9k input tokens against a 65.5k context. Result: 57% of concepts have no link.” Lectures L21, L27, L31 and L37–L63 (except L43, L46, L48) got none.

v3 finds relationships inside one segment, from that segment's facts only (stage 2c), and joins them across lectures in code (stage 3c). A prompt then never grows with the course: the 779 calls of 2c averaged about 3,700 input tokens (2,890,550 in all, stage_2c_concepts/llm/calls.jsonl). Every lecture has relationships; the course has 7,427. The price is decision D4 in the plan: a relationship between concepts taught in different segments is never found. It is listed under future work.

Judges set the run time. “2,711 judge + 1,035 rewrite calls: 58% of requests, 12.1 M of 18.0 M output tokens, 90%+ of it thinking, p50 latency 400 s.” v3 judges only what a learner sees (activities), caps thinking at 6,144 tokens, and measured its fact judge before letting it change anything. That measurement switched it off (stage 2b).

Fragmented, noisy registry. 1,019 of v2's 1,395 concepts appeared once; some aliases were sentences (“A virtual reality system is an artificial environment which…”). v3 checks every alias against the facts (alias_not_written: an alias must be written in a fact), never takes a sentence as a name, and joins the names with an exact merge plus a model decision per cluster.

Open questions dropped by a check. “70 questions dropped by the code check ‘each key point needs 2 keywords word for word in the reference answer’.” v3 ties a reference answer to its key facts (at least two) instead of keywords; every lecture has an open-question activity.

Against simpler approaches

Three simpler designs could answer a learner's question about a course. Here is how this pipeline differs from each, illustrated with real outputs. This first part is the argument from design. All three were then run on this course with the same model and the same questions; what that measured, wins and losses, is in What the method buys below.

(a) Plain LLM

Ask a model, no course data

It answers from what it learned in training. It cannot say which lecture taught a thing or at what minute, it cannot say “this course does not cover that”, and its definitions are the textbook's, not the lecturer's.

Measured: 0.254 correct, 61 false claims in 65 answers, 1 of 9 not-covered questions handled.

(b) RAG over transcripts

Search the lecture text, answer from chunks

It can cite lectures. But a chunk of speech is full of “this”, “it”, “as we saw”, acronyms and asides; a chunk that mentions a term is retrieved as readily as the one that defines it; and no chunk holds “what do I need before lecture 9”.

Measured: 0.815 correct, level with ours overall; ahead on structure and multihop questions, behind on definitions (0.786), prerequisites (0.125) and formulas (0.7).

(c) GraphRAG alone

An entity graph built from chunks

It adds entities and relations, often with community summaries. Without facts that cite sentences, a course order, a lecture graph and goals, it can relate concepts but not tell a learner where one is taught or what comes first.

Measured: 0.777 correct with its source text (twice RAG's context), 0.662 without; 0 on prerequisites.

  • Every claim leads to the video. An answer cites facts; each fact cites sentences; sentences have times. The learner sees “(lecture 8, 26:40)” and clicks it. From the vLLM benchmark (analysis/qa/bench_vllm_shipped.jsonl, B09): 
    {{S:qa_b09}}
  • “Not covered” instead of a made-up answer. Vergence-accommodation conflict is a real VR topic this course does not teach. The answer says so, then offers what the course does say (B02): 
    {{S:qa_b02}}
    A plain LLM would explain the conflict from its own knowledge, correctly perhaps, but not from this course.
  • Prerequisites from the lecture graph. “What do I need before lecture 30?” is answered from stage 4c, not from text that happens to match (B14): 
    {{S:qa_b14}}
  • Definitions with “where it is defined”. Each defined concept has one definition, written from its defining facts, with the lecture, segment and time where it is taught (the concept card).
  • Facts are cleaned before they are searched. A transcript sentence: “And it depends on the size and shape of the head, ears, and ear canal.” The fact built from it and two others: “Head-related transfer functions (HRTF) depend on the size and shape of the head, ears, and ear canal, and every person has a unique HRTF.” The pronoun is resolved, the acronym spelled out, the point whole. fact_lookup is retrieval too, but over 2,006 such facts, not over 206,605 words of speech.
  • Activities from the same verified store. A quiz question cites the facts that answer it, and a judge checked it against them (stage 5). Neither RAG nor a plain LLM produces a course's quizzes, crosswords and concept maps with that link.

What the method buys: measured against plain LLM, RAG and GraphRAG

The same 12B model answered 65 questions about this course through eight systems: ours, a plain LLM with no course data, RAG over the transcripts (with and without thinking), a GraphRAG-style index (with and without its source text), and two ablations of ours that keep only part of the knowledge layer. Every one of the {{BASE:n_judged}} answers was graded by one judge, Claude Sonnet, against a gold answer written from the transcripts; a second judge (Claude Opus) agreed on 257 of them with Cohen's kappa 0.715. How each system was built and run, all 65 questions and every table are in Evaluation: baseline tests. Everything in this subsection is measured, except the planned optimisation in point 4, which is marked argued.

The two ablations say which part of the layer earns each result. Fact search only is ours offered just fact_lookup (search over the 2,006 facts). Graph tools only is ours offered just check_concept, lecture_dependencies, lecture_overview and course_goals: the concept cards, the lecture graph, the lecture overviews and the goals, with no fact search. 1. Where ours wins, and which part of the knowledge layer causes it

{{BASE:wins}}

Mean correct (1 / 0.5 / 0) per category, run 1. “Not covered”: the course does not teach the topic; correct means the answer says so without inventing course content.

  • Definitions come from the concept cards. Ours and graph tools only score 1.0 on all seven; RAG 0.786, GraphRAG with text 0.786, fact search only 0.929. The clearest case is “What is vection?”: RAG and RAG with thinking both answer that the course does not cover it (retrieval missed lectures 11 and 26), fact search only gets half of it, and one check_concept call returns the card with its definition and times. On “What is an IMU?” RAG has the three sensors but not their role in correcting drift, which ours includes. {{BASE:ans_D06}}
  • Prerequisites come from the lecture dependency graph. “What do I need before lecture 17?” has no passage that answers it: the answer is a relation between lectures, which stage 4c computes from the concepts each lecture uses and defines. Graph tools only score 0.75, ours 0.5, and every baseline 0.125 or less; fact search only scores 0. RAG and RAG with thinking answer at least two of the four with a false “not covered”; the GraphRAG variants name no earlier lecture or the wrong ones. Over three runs ours stays at 0.5, RAG averages 0.042. The gap between ours and graph tools only is two half-points on four questions (P02 and P03), with near-identical answers. {{BASE:ans_P02}}
  • Formulas. Ours 0.9, RAG 0.7, the same in all three runs: a fact holds a formula with its terms and conditions, where a transcript chunk may hold half of it. RAG with thinking also reaches 0.9, but at a median 27.9 s per formula answer against ours' 5.2 s.
  • “Where is X taught?” Every system with course data scores 1.0 (the plain LLM 0): a tie: the layer answers it from fact times, RAG from chunk times.
  • “Not covered” and false claims. Ours handled 8 of 9 not-covered questions, RAG 9 of 9, the plain LLM 1 of 9. Ours made 5 false claims in 65 answers (one each in 5 answers), RAG 3, RAG with thinking 1, the plain LLM 61 (in 40 answers). So against a model without course data the layer removes almost every invented claim; against RAG it is level, not better. The ablations show where grounding comes from: fact search only made no false claim at all, graph tools only made 9 (6 of them on multihop questions), so the fact store is what keeps answers to what the course says.

2. Activities only the knowledge layer makes possible

The activities study (method) compares, on six lectures, the shipped activities with activities made without the layer by the same 12B model: B1, the whole transcript and a plain prompt per kind; B2, our own prompts, code checks and retry, with the transcript where the facts go. Ours on Gemma reruns our stage 5 on that same model, from the layer. Several kinds need the layer's structure and cannot be made from a transcript at all; two more can be attempted from one, and come out worse:

{{BASE:act_layer}}
  • Concept maps. Every edge of ours is a relationship from stage 2c with its type and facts (1,076 of 1,076 in the sample); the baselines' maps have no typed relationship (0%). The blind Sonnet judge found 97% of ours' sampled edges correct, against 75% for B1 and 69% for B2. Most of the baselines' wrong edges point the wrong way (“gaming is a kind of application domain”, read backwards): by the judge's reasons, 11 of B1's 18 wrong edges and 21 of B2's 22.
  • Recall before a lecture. Ours picks the earlier lectures from the lecture graph and the answers from 4a's definitions; the baselines were given the earlier lectures' titles. Sonnet found ours grounded in the course on 83% of items, B1 on 66%, B2 on 69%, and a wrong link between lectures on 6% against 11% and 14%. By code, the concept is found in the lecture the item names on 89% of ours, 80% of B1 and 74% of B2. Sonnet rated a few more baseline items correct (B1 97%, B2 100%, ours 94%): the baselines write plausible questions, but less often about what the named lecture actually taught.
  • Kinds the baselines cannot make: complete the map, match the pairs and crosswords are built from concepts, definitions and typed relationships; 1,316 spaced-review cards come from the defined concepts and every lecture that uses them. Every one of the 1,168 activities cites facts, so each item links to its minute of the video, and every one carries concept links to the glossary.

3. Activity quality without the layer

For the kinds a transcript can feed (quiz, recap, open question, odd one out, put in order), the answer is mixed, and it is stated as measured.

  • A plain transcript prompt is clearly worse. The pipeline's own judges (on Gemma) pass B1's quiz questions 65% of the time against 96% for ours on Gemma, open questions 10% against 83%, odd one out 29% against 73%, put in order 0% against 50%. B1's quiz key is the longest option 64% of the time (ours on Gemma 24%, shipped 10%), and the code check found source talk (wording that speaks of the lecture or the text instead of the subject) 87 times in its quiz items. Sonnet found B1's open questions grounded only 57% of the time. One exception: B1's recaps pass the Gemma judge more often (91%) than ours on Gemma (78%).
  • Our prompts and checks without the layer come close. B2 passes the Gemma judges on 99% of quiz questions and 98% of recap points (ours on Gemma 96% and 78%); it is a little behind on open questions (71% against 83%), odd one out (64% against 73%) and put in order (43% against 50%), and its retries left 1 quiz and 2 odd-one-out units of 6 unresolved. Sonnet rates nearly every item of every system correct on quiz, recap, open question and put in order. So for items about a single lecture, most of the quality comes from the prompts and the code checks with retry, which a transcript can feed too.
  • Where the shipped set is still ahead: Sonnet rated its quiz distractors good on 75% of questions (B1 43%, B2 51%), its quiz questions serving the lecture's goals on 80% (61%, 64%) and its recap points on 85% (68%, 75%). That gap mixes the layer with the writer and the judge: the shipped quiz items were written by Qwen 3.8 27B, the shipped recaps by Gemma 4 12B, and both went through the pipeline's judge (quiz items also through a rewrite). Ours on Gemma, the same-model comparison, lands between: distractors 55%, quiz goals 78%, recap goals 77%.
  • Where the baselines are ahead: on odd one out, Sonnet found the baselines' groups serving the goals more often (B1 64%, B2 57%, shipped 43%, ours on Gemma 36%), and rated 2 of the 14 shipped items incorrect. The lexical traceability check also favours the transcript-fed systems, as it should: they copy the transcript's words (quiz keys traceable: B2 89%, ours on Gemma 82%, shipped 77%).

A small sample: six lectures, and Sonnet saw at most 12 items per system and kind in a lecture (1,037 items in all). The Gemma judges see what each writer saw (ours its facts, B2 its transcript blocks, B1 the transcript window that best matches each item), so they measure faithfulness to each system's own input. Full tables: the activities study.

4. What it costs: once per course, then per question

Once per course. Building the layer and the activities took about 11 GPU hours: 10.8 h of measured stage time plus 0.5 h of reruns, about 11.3 h, with Qwen 3.8 27B on one 96 GB RTX PRO 6000 (2c on a 46 GB L40S). This is the sum of the stage times in Every stage in one line and Time estimates. Of it, stages 1a to 4d, the part question answering reads, are about 8.1 h (19 + 8 + 86 + 233 + 24 + 107 + 6.5 minutes); the rest is the activities. RAG's index, for comparison, is 738 chunks embedded in 27 minutes on a CPU.

Per question, the layer costs close to what RAG costs:

{{BASE:cost}}

Ours reads about 900 more context tokens than RAG at the median and makes 2.3 model calls where RAG makes 1: one round in which the model thinks and calls tools, then the answer, sometimes a second tool round. The 1.4 s between them comes from that extra call and from ours thinking in its first round (RAG does not think). RAG with thinking matches ours on formulas and lands close overall (0.808), but at a median 25.4 s, about 4.5 times ours.

Planned optimisation · argued, not measured

The tool rounds are the part of ours' time that RAG does not have. Question answering can be changed so that, instead of several tool rounds, one tool call fetches every concept and fact the question needs at once. The answer then takes about one tool call before it starts, the same shape as RAG's single retrieval and answer, so the latency should come close to RAG's. This has not been built or measured, and no number is claimed for it here.

5. Where RAG ties or wins

{{BASE:ties}}
  • Overall it is a near tie: ours 0.80, RAG 0.815, RAG with thinking 0.808, GraphRAG with text 0.777 on all 65 questions. The method's advantage is in specific kinds of question, not across the board.
  • Questions answered by one passage of one lecture (explanation, comparison, list) tie or go slightly to RAG: 0.929 against 1.0, 0.929 against 1.0, 0.875 against 1.0. When the answer sits in one stretch of speech, eight transcript chunks hold it, and the layer has nothing to add.
  • Course-structure questions: RAG 0.9, ours 0.6. Ours fails “What are the six modules of this course?” (it answers from the eight course goals and denies there are six modules) and “What topics does the course say it does not cover?”. Both answers are statements about the course itself, and fact extraction leaves those out by design: rule 7 of prompts/fact_extraction.txt says “On the subject, not on the course”, skipping what the course will cover, its objectives and how it is organised. RAG finds the closing lecture's summary sentence. This is a design choice, open for revision, not a bug. {{BASE:ans_S02}}
  • Multihop questions (12, each needing passages from several lectures): RAG 0.625, ours 0.5 (0.528 over three runs, RAG 0.625 in all three). Every system is weak here with a 12B model; graph tools only score lowest of the systems with course data (0.333). One failure mode is clear: M08 and M09 are phrased “What earlier ideas does X rest on?”, which sent ours to lecture_dependencies; the graph returned the course's general foundations (XR, the definition of a VR system, computer graphics) instead of the specific earlier facts (presence, the Simulator Sickness Questionnaire, the empirical-study method; the GPU and frame-rate needs), and ours scored 0 on both in all three runs where RAG scored 0.5. {{BASE:ans_M08}}
  • Citation validity, checked by code: RAG 255 of 279 written citations valid (91%), ours 195 of 244 (80%). The rule is the same for every system and lexical: half of the cited sentence's content words must occur in that lecture's transcript from 30 s before to 240 s after the cited time. Ours' sentences paraphrase facts (acronyms spelled out, pronouns resolved), and a fact's time can be its segment's start, which may lower ours' score; neither cause was measured, so the gap stands as reported. The lowest category is structure (7 of 17).
  • Speed: RAG answers in 4.2 s at the median and starts writing after 1.5 s; ours 5.7 s and 3.0 s (point 4).

Where it runs: the model on a server, the app with the learner

This split works because the pipeline does the heavy work in advance. What the server must do per question is small and stateless: run one model over a prompt of a few thousand tokens, a median of two times. Everything that is large (videos: 5.5 GB for the course) or private to the learner (progress, highlights, answers) stays local. The client already supports a model on another machine: a config with "launch": false and a port (or url) attaches to a running server, which is how every build stage reached the EC2 through an SSH port forward (pipeline/ec2.md).
