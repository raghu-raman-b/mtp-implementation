Estimate for a 63-lecture course from scratch: about 11 GPU hours on one 96 GB GPU, plus about 25 minutes to set up a fresh instance (mostly model downloads; pipeline/continue/PROMPT.md) and 1–5 minutes per model load. This is the sum of the measured stages above, which ran with different settings: 1a, 1b and 2a with 32 parallel requests and a 16k thinking budget, 2c on a smaller GPU. Running every stage at 128 parallel requests on the 96 GB card would likely be faster; that was not measured. Throughput to plan with (vLLM, Qwen 3.8 27B FP8, RTX PRO 6000): about 1,650–1,850 output tokens per second with 128 requests in flight, about 1,340 with 64, about 45 for one request alone. The lir-construction README measured the same model at 752 tokens per second with 32 requests.

Per question once built: median 4.9 s on a 12 GB RTX 5070, 4.5 s on vLLM; first words after about 3 s.

From a fresh clone to a running viewer

The outputs are in git, so the viewer needs no model run. The full history is about 19 GB; clone the last commit of pipeline/ only (pipeline/demo/README.md):

git clone --depth 1 --filter=blob:none --sparse https://github.com/raghu-raman-b/mtp-implementation.git
cd mtp-implementation && git sparse-checkout set pipeline
cd pipeline
python3 viewer/serve.py nptel_vr --no-qa      # http://localhost:8765 ; add ?dev=1 for developer mode

Python 3.11 or newer (configs are read with tomllib). The viewer and most stages need only the standard library. The question box (Ask) needs a model server and the query embedder; the four ways to run it, from no GPU to a cloud instance and a Windows laptop, are in Running the demo.

Each stage is one script with the course name, an optional --only and, for model stages, --llm <config>. Stages run in order; each reads the previous ones' folders. The full chain, as run on the EC2 queue:

A new course: put its subtitles under input/<course>/input/subs/, its titles.tsv (id, week, type, number, part, title, youtube_id) and a course.json written by hand from its syllabus (only title is required; the prompts use outline and syllabus). Stage 0a already runs on six courses (VR and five other MIT and NPTEL courses); only VR has been run through the whole pipeline.

Rerunning after a prompt change

Every model answer is cached by a hash of its request: the engine, the model path and the request body (prompt, schema, sampling, token limits, tools; for llama.cpp also the thinking budget, a server setting there). So:

  • Edit prompts/<stage>.txt and rerun the stage with the same config: only the changed requests reach the model; the rest are answered from llm/cache.jsonl in seconds. Then rerun the stages after it.
  • A config change that enters the request (model, sampling, max_tokens, think_budget) reruns everything of that stage. launch, attach_wait_s, slots and server flags do not: the 64- and 128-slot 96 GB configs share their hashes with qwen38_27b_vllm_6k.json.
  • 2b's rewriter must use 2a's config: it continues 2a's cached conversation (LLM.lookup).
  • A judge pass over finished activities only adds judge calls: writer requests are identical with or without --judge. The 2026-11-17 rewrite job found its 410 writer answers cached in 4 s.
  • To compare a variant without touching the outputs, write elsewhere: --out DIR exists on 2c, 3a–3c, 4a, 4b and 5; --seed N on 2c, 4a, 4b and 5.

The EC2 workflow

The repository, outputs and caches live on the local PC; the EC2 only serves models, or runs a queue of stages so long runs go on without the local session (pipeline/ec2.md). The same config file is used on both sides: on the EC2 scripts/llm/serve.py starts the server from it; locally the stages attach ("launch": false, waiting up to attach_wait_s, 30 min) and refuse a port that serves another model.

# once per instance (and after every stop: the NVMe model cache is wiped); ~25 min, mostly downloads
rsync -a --exclude __pycache__ --exclude 'input/*/media' --exclude 'output/logs' --exclude '.hf_token' pipeline/ mtp:pipeline/
ssh mtp "mkdir -p pipeline/output/logs && tmux new -d -s setup 'bash ~/pipeline/setup_ec2.sh 2>&1 | tee ~/pipeline/output/logs/setup.log'"

# A. run stages from the local PC against a model server on the EC2
ssh mtp "tmux new -d -s qwen 'cd ~/pipeline && python3 -m scripts.llm.serve configs/qwen38_27b_vllm.json'"
ssh -f -N -L 8094:127.0.0.1:8094 -L 8095:127.0.0.1:8095 mtp
python3 scripts/s2a_fact_extraction.py nptel_vr --llm configs/qwen38_27b_vllm.json --only 1,4,16

# B. or queue them on the EC2 (each job: "<qwen|sage|none> <command>")
ssh mtp "cd pipeline && tmux new -d -s queue 'QWEN_CFG=configs/qwen38_27b_vllm_6k_96gb.json bash ~/pipeline/ec2_queue.sh'"
ssh mtp "echo 'qwen python3 -u scripts/s3b_same.py nptel_vr --llm configs/qwen38_27b_vllm_6k_96gb.json' >> pipeline/queue/jobs.txt"
ssh mtp tail -f pipeline/queue/queue.log
# from the repository root; the 2026-11-17 rebuild ran with configs/qwen38_27b_vllm_6k_96gb.json
bash pipeline/rebuild_queue.sh configs/qwen38_27b_vllm_6k_96gb.json    # queues 3b, 3c, 4a, 4b, 4c, 4d
  • ec2_queue.sh runs queue/jobs.txt line by line, starting the server each job needs and stopping the other (each takes about 92% of the GPU); done jobs go to queue/done.txt, logs to queue/logs/<line>.log. A failed job stops the queue until touch queue/resume (skip it) or touch queue/retry. A job can wait for a go-ahead, as the 2026-11-17 rebuild did before 4a: bash -c 'until [ -f queue/go_4a ]; do sleep 20; done'.
  • bash pipeline/continue/progress.sh makes the local tmux session mtp: a status view, the logs, and a sync loop that copies the EC2's output/ and queue/ into ec2_sync/ (gitignored) every 5 minutes. Results are merged into pipeline/output/ (the local cache must be a prefix of the EC2's) and committed.
  • Qwen loads in about 1 minute with its weights in the page cache, 5 cold; Sage in about 5. The 27B FP8 does not fit a 32 GB card (weights about 28 GB); nvidia/Qwen3.8-27B-NVFP4 is the noted fallback.
  • No real model runs except on an instance the user started; plumbing is checked first with fake servers (tests/fake_*.py).

1. No GPU: the viewer only, Ask off

Every page works (lectures, activities, maps, glossary, videos); the question box is off, so nothing loads a model, the embedder or numpy. Any OS with Python 3.11 or newer. --no-qa (the viewer, the launcher and run_demo.ps1) is new on 2026-11-19.

python3 viewer/serve.py nptel_vr --no-qa                                      # any OS
python -m demo run --no-qa                                                     # the same through the launcher
powershell -ExecutionPolicy Bypass -File pipeline\demo\run_demo.ps1 -NoQa      # Windows, after setup_windows.ps1

Videos (5.5 GB) are not in git and are optional: the viewer reads input/nptel_vr/media/ or the folder given with --media, and plays a lecture without a file from YouTube (by the youtube_id in titles.tsv; the machine then needs internet). --prefer-youtube (or ?yt=1) uses YouTube even when the files are there.

2. Local GPU: llama-server started by qa

How the local PC runs it, with Gemma 4 12B QAT on its 12 GB RTX 5070 (median 4.9 s per question). Needs:

  • an NVIDIA GPU and llama.cpp's llama-server built for it (the PC runs commit 69eb250, built 2026-09-15, the LLAMA_REF of the instance script);
  • the model unsloth/gemma-4-12B-it-qat-GGUF, file gemma-4-12B-it-qat-UD-Q4_K_XL.gguf (revision 980b060, 6.72 GB);
  • the query embedder in the same Python: numpy, torch==2.14.1, sentence-transformers==6.1.0, transformers==5.15.0; Qwen/Qwen3-Embedding-0.6B (1.2 GB) downloads on first use;
  • the config configs/gemma4_12b_llamacpp.json (port 8092, 6 slots, 131,072 context, q8_0 KV cache, thinking budget 8,192). It names this PC's binary and model_path and runs the server in the Fedora toolbox llm-engine. On another machine set binary and model_path and set toolbox to "" (else the start stops: “toolbox is set in the config but the toolbox command is not installed”), or give another config with QA_CONFIG.
python3 viewer/serve.py nptel_vr --warm          # Ask on; loads the layer, the embedder and the model at start
python3 -m qa "What is an HMD?" --lecture 4      # one question from the command line
python3 -m qa --stop                             # stop the llama-server on the config's port

How qa starts and stops its server. The local config does not set "launch": false, so the client launches: at the first question, or at start with --warm, it checks the config's port. When nothing answers it starts llama-server with the config's flags (inside the toolbox when one is set) in a session of its own, logs to output/logs/llm_server_8092.log, waits for /health and attaches. A server that already answers on the port is used as it is; one that serves another model is refused. The server is left running when the viewer or python -m qa exits, so the next start does not wait for the load. python3 -m qa --stop stops it (pkill of llama-server on the config's port; Linux and macOS only, and not for a config that points at another machine). Without --warm, the first question that searches the facts waits 20–23 s for the embedder to load.

3. Remote GPU instance: the model there, everything else here

The instance only serves the model and the query embedder, both on 127.0.0.1 (no port open but SSH). The viewer, qa's tool loop, the layer and the videos run on the laptop; only the model's requests (a few thousand tokens of text per call) and the embedder's queries cross the tunnel (the design, pipeline/demo/README.md section A).

The instance needs an NVIDIA GPU with the AMI “Deep Learning Base OSS Nvidia Driver GPU AMI (Ubuntu 24.04)” (driver, CUDA toolkit, Python 3.12; on Ubuntu 22.04 install python3.12 and set PYTHON=python3.12), a security group with SSH only, a 100 GB root volume. For llama.cpp any NVIDIA GPU with 16 GB or more (a g6.xlarge with an L4 or a g5.xlarge with an A10G is enough). For vLLM 40 GB or more (an L40S, an A100, the RTX PRO 6000: it serves the BF16 checkpoint, 24 GB of weights; FORCE=1 overrides the check) and a Hugging Face token with access to google/gemma-4-12B-it (HF_TOKEN or pipeline/.hf_token). vLLM was benchmarked at a median of 4.5 s and a maximum of 6.6 s per question on the RTX PRO 6000, with the viewer on the same machine (configs/gemma4_12b_vllm_demo.json, analysis/qa/STATE.md).

# from the laptop: copy the ~150 kB the instance needs to ~/mtp-demo/pipeline, run the setup there in tmux "setup",
# and show its output (--no-start: copy only)
python -m demo push --instance ubuntu@<ip> --key ~/demo.pem --engine llamacpp      # or --engine vllm

# or on the instance itself
bash ~/mtp-demo/pipeline/demo/ec2_model_server.sh --engine llamacpp     # or --engine vllm; no flag: it asks
bash ~/mtp-demo/pipeline/demo/ec2_model_server.sh --status              # which ports answer, the tmux sessions, the tunnel command
bash ~/mtp-demo/pipeline/demo/ec2_model_server.sh --stop                # stops both servers (tmux model and embed)

ec2_model_server.sh, in eight steps: the GPU (and the 40 GB check for vLLM), the Hugging Face cache on the local NVMe when there is one, the token; the missing system packages (tmux, curl, python3-venv; for llama.cpp also git, cmake and build tools); ~/demo-venv with torch and sentence-transformers at the versions the facts were embedded with, while the model and the embedder download; the engine (llama-server built for this GPU at the PC's llama.cpp commit, or vLLM in ~/vllm-venv); the demo config set for this instance (configs/gemma4_12b_demo.json or gemma4_12b_vllm_demo.json); tmux model (the model server on 127.0.0.1:8096, started by scripts/llm/serve.py from the config) and tmux embed (demo/embed_server.py on 127.0.0.1:8097); two warm-up requests (a short one, then one with the qa tools and thinking); the tunnel command and the laptop's command. It is safe to rerun: what is installed, built or downloaded is reused, a server that answers is kept, and switching the engine stops the other one first. --no-embed serves no embedder (the laptop then embeds on its CPU with --local-embed). The other options are environment variables listed at the top of the script (TORCH_CPU=1, NO_NVME=1, LLAMA_REF=master, VLLM_PKG, PYTHON, FORCE=1). The README expects about 20 minutes the first time and 2–3 after (not yet measured on an instance). Stopping the instance wipes the NVMe and with it the model cache: the next start downloads again.

The laptop (Linux or macOS; Windows in setup 4):

pip install -r demo/requirements-local.txt                                      # numpy
python -m demo setup --instance ubuntu@<ip> --key ~/demo.pem --media ~/videos    # saves demo/local.json, checks this machine
python -m demo run                       # tunnel + viewer + browser; Ctrl+C stops the viewer and the tunnel
python -m demo check                     # in a second terminal: PASS / FAIL lines, ALL PASS at the end
python -m demo bench --warmup            # the demo questions through the stream, timed
python -m demo tunnel                    # only the tunnel, in the foreground
  • setup saves the instance, key, videos folder and --local-embed in demo/local.json (gitignored; the other commands take them as defaults) and checks Python 3.11 or newer, numpy (and sentence-transformers with --local-embed), ssh on the path, the key file, the videos in the folder, and the course layer.
  • run opens the tunnel ssh -N -L 8096:127.0.0.1:8096 -L 8097:127.0.0.1:8097 user@host (ServerAliveInterval 15, ExitOnForwardFailure; opened again when it drops), waits up to 30 minutes for the model server (it may still be loading), reads the engine from the served model's name (gemma-4-12b-qat llama.cpp, gemma-4-12b vLLM), writes that engine's demo config with url = the tunnel to demo/logs/qa_remote_<engine>.json, checks that the embedder serves the layer's model, starts viewer/serve.py --warm with QA_CONFIG, QA_EMBED_URL and QA_KEEP_WARM=1, waits until /api/qa_status says ready, and opens the browser. The instance keeps serving after Ctrl+C. Options: --port (8765; the next free port when taken), --media, --prefer-youtube, --no-browser, --no-tunnel (the ports are already forwarded), --model-port N (when 8096 is taken on the laptop), --local-embed, --wait-model (1800 s), --wait-warm (180 s), --no-qa.
  • check prints PASS, FAIL or SKIP per item and exits with 1 on a failure: the viewer answers; the model server is healthy through the tunnel (with its time) and serves a demo model; question answering is warm; the embedding server serves the layer's model, and its vectors for 24 fact texts equal the layer's (cosine ≥ 0.999); the viewer routes /, /api/home, /api/view/4, /api/glossary; one question (“What is an HMD?”, --question) answered through the stream with at least one citation, with its times. With the PC standing in for the instance through the simulated 250 ms tunnel: ALL PASS, health check 505 ms, minimum cosine 0.99977, first words after 4.19 s, done in 7.64 s, 4 citations (remote_setup.md).
  • bench asks the 12 questions of DEMO_PLAN.md (the list in launcher.py) through /api/ask_stream and prints, per question and as medians, the seconds to the first event, the first step, the answer's start, the first words and the end. --warmup asks an off-stage question first; --runs N; --out FILE appends one JSON line per question; several --url compare setups question by question.
  • push and tunnel: above; both take --instance, --key, --ssh-port.

The network, first. Time SSH to the instance before choosing it: time (ssh -i key.pem ubuntu@<ip> "head -c 2000000 /dev/urandom" | wc -c) should take under about 2 s. From the user's network, SSH to us-east-1 ran at about 40 kB/s: pick an instance in a region near the venue. Each new connection through the tunnel costs a round trip, so qa keeps its connections to both servers open (scripts/llm/http_pool.py); through the simulated 250 ms tunnel the first byte of a round came after 338 ms instead of 589 ms.

Python API

Question answering: qa

from qa import answer, answer_stream, warm

r = answer("What is an HMD?", course="nptel_vr", lecture="4")      # lecture: optional
r["answer"]      # text, citations written as "(lecture 4, 6:01)"
r["citations"]   # [{"fact", "lecture", "segment", "start", "end", "text"}]
r["steps"]       # [{"tool", "args", "result_summary"}]
r["covered"]     # True for "COVERED: yes" or "partly"

for ev in answer_stream("What is an HMD?", course="nptel_vr"):
    ...          # {"event": "step", "tool", "args", "result_summary"}   after each tool call
                 # {"event": "draft", "text"}       the answer so far (replaces the previous draft)
                 # {"event": "reset"}               text of a round that ended in tool calls is not the answer
                 # {"event": "done", "result": {...}}   what answer() returns

warm("nptel_vr")  # load the layer and the embedder, start or attach to the model server

Also exported: get_llm(config, think), Knowledge (the layer: Knowledge.load(course)), run_tool(kb, name, args), tool_specs(). Module switches in qa.answer: MAX_ROUNDS = 5 (at most 5 rounds of tool calls, then one answer round), ROUND0_THINK = True, ROUND0_TOOL_CHOICE = "auto". Tool constants in qa.tools: CARD_FACTS = 10, LOOKUP_K = 8, LOW_SCORE_DEFAULT = 0.55, UNKNOWN_K = 5, DEP_MIN_USES = 2.

The LLM client: scripts.llm

from scripts.llm import LLM, LLMConfig, Request

cfg = LLMConfig.load("configs/qwen38_27b_vllm_6k_96gb.json")      # .json or .toml; cfg.with_(slots=8) a changed copy
llm = LLM(cfg).start()            # attach to a running server, or launch one when "launch" is true
req = Request(prompt="...", key="lec_5", schema={...}, check=lambda parsed: [], feedback=True)
res = llm.generate(req, cache_file="out/llm/cache.jsonl", log_file="out/llm/calls.jsonl")
res.ok, res.parsed, res.content, res.reasoning, res.errors, res.input_tokens, res.output_tokens, res.cached
many = llm.generate_many([req, ...], parallel=True)               # all at once; results in request order
llm.lookup(req, cache_file=...)   # a cached answer without sending
llm.stop()                        # stops only a server this LLM started

Request also takes system, followup (more turns), max_tokens, think_budget, sampling, meta, tools, tool_choice; Result has tool_calls, history, finish, attempts, hash, latency_s. Server side: python3 -m scripts.llm.serve <config> [--smoke] starts the server a config describes and keeps it running (Ctrl-C or a hang-up stops it). scripts/llm/fake_server.py answers like vLLM with JSON built from the request's schema, for tests.

Stages as functions

Every stage script has run(), e.g. s1a_segmentation.run(course, llm, lectures=None, parallel=True), s1b_verify_segments.run(course, lectures=None, llm=None), s2c_concepts.run(course, llm, lectures=None, seed=None, out=None), s3a_candidates.run(course, lectures=None, embed_model=…, threshold=0.70, cap=12, …), s4a_definitions.run(course, llm, cap=40, seed=None, out=None), s4c_lecture_graph.run(course, params=None), s5_activities.run(course, llm, only=None, kinds=None, …). scripts.view.Course(course) loads every stage's output into dicts for a notebook (c.sentences["1/0"], c.segments["1/S0"], c.lecture(1)). scripts.embed.Embedder(model, cache, device).embed(texts, instruction=None) returns L2-normalised vectors.

Running the tests

The tests need no GPU: a fake model server answers with JSON built from each request's schema, on a free port, in a temporary copy of the pipeline folder. Each test lists what it would look like if the stage were broken and seeds known errors. Run them from pipeline/; each ends with PASS or the failing checks. Stop the SSH port forward before fake_run.py (it uses the EC2 configs' ports 8094 and 8095), and run them when no other run is writing logs under output/logs/.

python3 tests/fake_run.py          # 2a and 2b on lectures 1, 4, 16 through the EC2 configs: caches, model swap, no output touched
python3 tests/fake_2c.py           # stage 2c: checks, retries with feedback, best attempt kept (44 checks)
python3 tests/fake_registry.py     # stage 3: exact merge, candidates, groups, merge log, relationships rebuilt
python3 tests/fake_knowledge.py    # stages 4a-4d: definitions, goals, lecture graph, the layer and its check
python3 tests/fake_activities.py   # stage 5: every kind, code checks, the judge and rewrite paths, the contract
python3 tests/fake_qa.py           # the tool loop, citations, early exit, streaming, the vLLM config; --layer DIR
python3 tests/viewer_smoke.py      # every route, 304/gzip, versioned static files, Range, /api/ask_stream
