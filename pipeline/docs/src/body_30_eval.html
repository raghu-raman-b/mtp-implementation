What fails where, and how each failure is handled

Every failure kind found in the course as built, stage by stage, with its count and how it is handled. Two rules held (the user's, 2026-11-18). A failure is found only by code: a rule, a pipeline check file, the pipeline's own judge verdict, or a stored similarity; no language model and no agent decided what a failure is. And a failure is handled only by the pipeline itself or by a display rule that uses the pipeline's own signal (the judge's verdicts, 4a's defined flag, 4c's graph); nothing was fixed by a stronger model or by a hand-made list. So duplicate concepts and odd aliases, which code finds but no pipeline signal resolves, are listed as not fixed (future work).

The handling values: fixed in the pipeline (a check with retry, a rewrite, a stage that was redone); fixed in the viewer (rendering); display rule (the data is kept; the viewer shows a part of it, chosen by the pipeline's own signal); hidden from learners (the item is kept and shown only in developer mode); not fixed (future work).

Baseline tests: question answering against plain LLM, RAG and GraphRAG

The full method behind What the method buys in Part I. Eight systems answered the same 65 questions on this course with the same model; one judge graded every answer; code checked every citation. Everything here comes from baseline-tests/ (commit 0d7f665): README.md (method), questions.jsonl, judgments.jsonl, summary.json and tables.md (results), run_stats.md, judge_agreement.md; raw answers in runs/. The tables on this page are computed from copies of those files (pipeline/docs/src/baselines/).

Model and sampling, the same for every system

  • Gemma 4 12B QAT (unsloth gemma-4-12B-it-qat-UD-Q4_K_XL.gguf) on one llama-server (llama.cpp), config pipeline/configs/gemma4_12b_llamacpp.json: context 131,072, 6 slots, KV cache q8_0, reasoning budget 8,192 tokens. Run on a local RTX 5070 (12 GB), one question at a time per system.
  • Sampling: temperature 1.0, top_p 0.95, top_k 64 (question answering's own config), for every call of every system.
  • Thinking: ours and the two ablations think in their first round only (as question answering ships); RAG with thinking thinks in its one call (same 8,192-token budget, max_tokens 12,288); the plain LLM, RAG and both GraphRAG variants do not think (max_tokens 2,048).

The ablations replace the tool list question answering offers, and answer a call to a removed tool with its own “There is no tool …” result; prompt, tool descriptions, rounds and everything else stay as shipped, and pipeline/qa itself is not modified. The first ablation runs were invalid: the patch bound the function qa.answer instead of the module, so both ran with every tool (found when they gave the same answer on 52 of 53 questions). The patch was fixed, checked (fact search only is offered one tool, graph tools only the other four), and both were rerun and re-judged; the invalid runs are kept apart and used only in the judge-agreement check.

The questions

65 questions, each with a gold answer and gold sources (fact or sentence IDs with lecture and time), written from the transcripts (make_questions.py): definition 7, explanation 7, comparison 7, list 4, formula 5, where 5, prerequisite 4, structure 5, not covered 9 (the course does not teach the topic; the right answer says so), multihop 12. They include the demo plan's questions and the QA bench's B-questions. The 12 multihop questions (M01–M12, questions_multihop.md) were written without looking at any system's output and checked against the transcripts; each needs passages from three to seven lectures, in four kinds: a chain of causes across lectures, a topic spread over more lectures than a top-8 search covers, the course order, and a link between two concepts that the course states only in pieces.

Runs

Run 1: every system on all 65 questions. Runs 2 and 3: ours, RAG and RAG with thinking on the 40 questions of the categories where they differ most or that test reliability (not covered, where, prerequisite, structure, formula and multihop); same settings, only sampling differs. Recorded per answer: wall seconds, time to the first answer token (ours: the first streamed draft), retrieval seconds, context and output tokens, model calls. No run had an error. The repeats vary little: across the three runs, ours gave the same answer text on 29 of the 40 questions, RAG on 15, RAG with thinking on 39 (counted from runs/ for this page), and the category means hardly move:

Judging

  • One judge for every answer: Claude Sonnet graded all {{BASE:n_judged}} answers (8 systems × 65 in run 1, plus 3 systems × 2 runs × 40), four judges in parallel on disjoint sets. Each saw the question, its category, whether the course covers it, the gold answer, and every system's answer labelled with the system's name; none saw earlier judgments.
  • Criteria, one line per answer: correct 1 (the gold's main points, nothing wrong), 0.5 (partly right or incomplete) or 0 (wrong, empty, or a false “not covered”); on not-covered questions, 1 means it says the course does not cover the topic. hallucinations: the number of false claims, contradictions of the course, or outside content presented as taught. not_covered_handled (not-covered questions only): said not covered and invented no course content. A note of at most 12 words.
  • Second judge: an earlier pass by Claude Opus graded 257 of the same answers (ours, plain and RAG on the first 53 questions, and the invalid ablation runs). Agreement on correct: exact 0.864, never more than half a point apart, Cohen's kappa 0.715; on whether an answer has a false claim, 0.930. Opus is more lenient (ours 0.915 under Opus, 0.868 under Sonnet; plain 0.396 and 0.255), but both judges rank the systems the same way. The 35 disagreements are listed in judge_agreement.md.
  • Citation validity, by code (the same rule for every system, summarize.py): each “(lecture N, m:ss)” an answer writes is valid when the lecture exists and at least half of the content words of the sentence it closes occur in that lecture's transcript from 30 s before to 240 s after the cited time.

Limits of this test

  • One course and 65 questions; a category has 4 to 12 questions, so one question moves its mean by 0.04 to 0.125 (a half point) or 0.08 to 0.25 (a full point).
  • One model size: Gemma 4 12B for every system. The layer itself was built with Qwen 3.8 27B, so ours carries the work of a larger model done once, offline; that is the method, and it is the cost in point 4 of Part I.
  • One judge family. Sonnet graded everything; Opus agreed with kappa 0.715 on 257 answers.
  • The repeats vary little (most answer texts are the same in all three runs), so they show stability under these settings, not the full spread of sampling.

From baseline-tests/. The llama-server on port 8092 is started by question answering on first use, or by python -m qa "hi" in pipeline/; python -m qa --stop stops it.

python3 graphrag_build.py extract         # resumable extraction -> graphrag/extractions.jsonl
python3 graphrag_build.py graph           # merge, Louvain, community reports, embeddings -> graphrag/
python3 run_systems.py ours plain rag rag_think graphrag_text graphrag_notext abl_facts abl_graph
for r in 2 3; do python3 run_systems.py ours rag rag_think --run $r \
    --categories not_covered where prerequisite structure formula; done
for r in 2 3; do python3 run_systems.py ours rag rag_think --run $r --categories multihop; done   # as queue.sh ran them
python3 render_for_judge.py               # judge/todo_*.txt: answers not yet in judgments.jsonl
# judge them into judgments.jsonl (fields above), then
python3 summarize.py                      # summary.json, tables.md, examples.jsonl, demo_questions.json
python3 judge_agreement.py                # judge_agreement.md: Opus vs Sonnet on the 257 answers both judged

The activities study

Question answering is half of what the layer is for; the other half is activities. A second study (baseline-tests/activities_study/) asks two questions: which activities are only possible with the knowledge layer, and how activity quality drops without it, at the same kinds and counts.

  • Sample: six lectures chosen by code: of the 35 lectures whose activities include every kind of the study (quiz, recap, open question, odd one out, put in order, concept map, recall), six evenly spaced in course order: lectures 2, 18, 28, 39, 51 and 62.
  • Ours: the shipped activities (activities/lec_<n>.json, not regenerated). Their quiz, open question, odd one out and put in order were written by Qwen 3.8 27B (with its judge and one rewrite), recaps by Gemma 4 12B; recall and concept maps are code.
  • Ours on Gemma: our stage 5 run again on the same Gemma 4 12B as the baselines, from the layer, for the five model-made kinds, with its code checks and retry and no judge (the baselines get no judge either). This makes the comparison same-model; recall and concept maps are code from the layer, so they are the shipped ones.
  • B1, plain: the whole lecture transcript and a short plain prompt per kind asking for the same JSON; one call per lecture and kind; JSON schema enforced; no code checks, no retry beyond unparsable answers.
  • B2, our prompts without the layer: our own activity prompts with the whole transcript, numbered by sentence, where the facts go; the layer's other inputs (sub-goal, objective, lecture goal, related concepts, relationships) given as “(not given)” or “(none)”; stage 5's own code checks with retry and its conversion. Concept maps and recall have no prompt of ours (they are code), so both baselines get B1's prompt for them, B2 with the numbered transcript and sentence citations.
  • Counts: each baseline is asked, per lecture, for as many items of each kind as ours has. All Gemma requests use the pipeline's client, sampling and cache, thinking on, max_tokens 24,576.
  • Grading, three ways: (1) the pipeline's own activity judges on Gemma, one round, no rewrite, for the five judged kinds, each seeing what its writer saw (B1 cites nothing, so each B1 item is shown with the transcript window that best matches it); (2) code checks on every item: schema, duplicates, cites sources, traceable (at least 60% of the key text's content words in one 3-sentence window of the transcript), quiz key position and length, source talk, concept-map ends found together with a typed relation, recall naming an earlier lecture that has the concept; (3) a blind Sonnet judge per lecture, the systems shuffled per unit as sets X / Y / Z with no IDs, grading each item for correct, grounded, distractors, fit to the lecture's goals and use of earlier lectures.
  • Only possible with the layer: counted from ours over the course and the sample: recall, typed concept maps, complete the map, match the pairs, crosswords, spaced-review cards, fact IDs, concept links, and open questions on earlier lectures' facts.
